# Klei Gift Watcher（Android 原生项目）

**这是一个可编译的 Android 项目源码包，不是已经验证运行的 APK。**

面向《饥荒联机版》Klei Creator Link 礼物：检查指定 B站 UP 主发布的动态，提取科雷礼物链接，并在手机端**尽力自动执行领取**。无需 Docker、服务器、外部机器人或上传账号密码。

## 功能

- 默认监控 UP 主 UID：`12875864`，可编辑。
- 新增最新动态 ID、发布时间、抓取通道、动态数量、最近错误及本地日志面板。\n- 可选锁屏增强：CPU 部分唤醒锁（高耗电，建议连接电源，不能绕过系统网络限制）。\n- 已启动监控时，开机或更新后可尝试自动恢复（Android 版本和厂商限制可能阻止）；前台服务被回收时请求系统重启。\n- 双通道轮询：网页 WebView **10～3600 秒**（默认 15 秒），备用 API **30～90 秒**（默认 60 秒）；网页可以解析动态时跳过 API 请求。
- 前台服务轮询，在通知栏显示“监控运行中”；可停止。刷新频率越高，电量及移动数据消耗越明显。
- 解析 B站动态 JSON 及近期部分图文正文，匹配：
  - `https://accounts.klei.com/creatorlink/...`
  - `https://accounts.klei.com/link/...`（常规科雷奖励链接）
- 新链接去重、保存本机记录、发送通知。
- App 内 WebView 登录科雷网站或 B站；Cookie 只保存在手机应用 WebView 存储中。
- 检测到新链接后可关闭自动领取，仅通知；开启时尝试用已登录会话打开链接并点击标准领取按钮。
- 可粘贴某个链接进行手动测试；支持从记录中再次尝试或进入页面手动领取。

## 构建 APK（推荐：GitHub Actions，无需自己安装 Android SDK）

1. 新建一个 GitHub 仓库，上传这个压缩包**解压后的所有文件和目录**，确保仓库根目录能看到 `settings.gradle.kts` 和 `.github/workflows/build-apk.yml`。
2. 在仓库 `Actions` 页启用工作流 `Build Android APK`，点击 `Run workflow`；推送到 `main` 也会触发。
3. 等构建完成后，在该工作流运行页面的 `Artifacts` 下载 `KleiGiftWatcher-debug-apk`。
4. 解压 Artifact，得到 `app-debug.apk`；复制到 Android 手机安装（允许对应来源安装未知应用）。
5. GitHub Actions 用 Java 17、Gradle 8.9、Android Gradle Plugin 8.7.3 编译。

也可以用 Android Studio 打开根目录，配置 JDK 17 和 Gradle 8.9 后执行 `:app:assembleDebug`。当前源码包不包含 Gradle Wrapper 的二进制 JAR，建议优先按上面的 GitHub Actions 方法构建。

## 使用顺序

1. 首先点击 **登录科雷账号**。在嵌入的 Klei 页面选择 Steam 或其它平台，完成登录，**核对是否为打算领取奖励的科雷账号**。
2. 如果 B站 API 报 `-352`、`412` 或需要登录，可点击 **登录 B站（可选）**，登录后返回 App；接口可能依然受风控。
3. 设置 UP 主 UID、网页刷新间隔与备用 API 间隔；勾选“自动尝试领取”。
4. 点击 **保存并启动监控**。
5. 在“领取记录”中检查执行状态：
   - `发现新链接`：已检测，尚未确认领取。
   - `已点击领取按钮，等待网页反馈`：已尝试网页交互。
   - `网页显示已领取（请核实账号）`：页面出现成功提示，但不是官方服务器的可验证回执。
   - `需要在 App 内重新登录` / `未找到领取按钮`：请打开链接手动处理。
6. 可以先粘贴一个之前已经领过或无效的 Klei 链接，验证登录与跳转流程，不建议直接用仅有一次机会的稀有礼物进行首次测试。

## 自动领取能力边界（请务必阅读）

- Klei 官方 Creator Link 页面可能要求登录、验证码或人工确认。**本程序并没有 Klei 官方授权的领取 API；采用 WebView 网页自动化，属于实验性功能。** 未找到按钮、页面结构变更、网页登录失效时不能保证领取。
- 手机上的离屏 WebView 在不同厂商设备上运行行为不完全相同。锁屏、省电策略、断网或进程终止均可能阻止自动操作。不要把它当作稳定的 24×7 服务。
- `已点击`、`已尝试` **不等于成功**；即使页面含有成功字样，仍应登录科雷网页核对奖励账户。Klei 明确提示奖励可能无法迁移到另一个账号。
- Steam 等平台可能禁止 WebView 内登录。如果登录环节被拒绝，不能通过外部浏览器登录来直接共享 App 内 WebView Cookie；请用 App 的手动查看链接功能或改用浏览器人工领取。
- Android 14+ 要求指定前台服务类型。本项目 `targetSdk=34` 是私人侧载调试版配置；**不代表绕过系统后台限制**，后续 Android 版本或应用商店政策可能要求适配。后台长时间持续轮询无法保证。
- 网页刷新最低 **10 秒**（默认 15 秒），备用 API 间隔 **30～90 秒**（默认 60 秒），仅当网页没有可读动态或手动检查时使用备用 API；不是两个通道同时高频请求。\n- 真实网页本身可能请求 B站 API，**网页刷新无法保证避开 HTTP 412**。遇到 HTTP 412 或 API -352，两个通道会共同冷却 2/5/15 分钟，不进行无限快速重试。\n- 网页检测依赖 WebView 在后台成功渲染动态卡片，不同手机版本、B站网页结构和登录要求可能导致检测失效，失效后会回退 API。\n- 发现同一链接只自动处理一次；可以手动点“重新尝试”。
- B站动态接口为社区文档记录的网页接口，可能变更或加风控；图文的部分内容可能无法通过当前解析器发现。检测失败会写进界面状态，不会假装成功。
- `https://accounts.klei.com/creatorlink/` 为 Klei 官方 Creator Links 格式：<https://support.klei.com/hc/en-us/articles/48344703634324-Creator-Links>。

## 隐私、安全与发布

- 不要在 GitHub 仓库添加 Klei Cookie、SESSDATA、密钥、验证码或密码。
- 程序没有远程数据采集服务；网络请求仅发往 B站动态 API、科雷网页及其登录平台。历史记录在 Android SharedPreferences，WebView Cookie 由 Android WebView 管理。
- 本项目只允许自动打开 `https://accounts.klei.com/creatorlink/...` 或 `/link/...`，**不是通用的任意网址执行器**。
- Debug APK 使用调试签名，适合自行安装测试，不适合未经评估直接公开上架或大规模发布。

## v0.3.0 · 后台监控须知

- 勾选「锁屏增强」后，前台监控服务将持有 PARTIAL_WAKE_LOCK：屏幕可以关闭，但 CPU 尽可能保持活跃。**非常耗电和可能发热**；推荐充电或先进行 30 分钟测试。关闭监控会释放唤醒锁。
- 点击「打开系统后台设置」，在手机系统中手动设置电池策略为无限制，并允许自启动、通知（如果有）。Android 没有通用且可靠的强制保活方式。
- 安卓 15+ 及更高版本可能限制 dataSync 前台服务；面向 API 35 及以上目标版本时，该类型前台服务有累计 6 小时/24 小时的时长限制，且不能通过开机广播直接启动。当前 targetSdk 为 34，但这并不保证所有系统能够 24 小时连续运行。
- 运行日志中的“成功检测”表示取到了动态卡片或列表，不意味着 Klei 奖励已确认领取；网页发布时间解析不到时显示“无法解析”。

## v0.3.1 网页无法识别动态时的诊断

- 首页新增“打开 B站动态网页诊断”，在 App 内实际显示 UID 对应的动态页面。
- 如果能看见动态，请点击“检测当前可见网页的动态卡片”，检查动态数量、最新 ID 和当前页面地址。如果能看见页面但卡片数为 0，多半是页面结构变化或 CSS 选择器未适配。
- 网页扫描新增更多卡片选择器，并多次等待动态 JavaScript 渲染；失败日志将显示标题、当前页面地址与少量页面片段，便于区分登录提示、空页面和网络问题。
- WebView 背景加载是 Android 的实验性路径，不保证锁屏时像可见浏览器一样渲染；遇到失败会回退 API。
- **备用 API 的请求频率现有硬性下限**：连续网页失败不会把设置的 30～90 秒 API 间隔缩短成网页检测间隔。
- HTTP 412 / API -352 仍会暂停轮询，不会采用代理、风控绕过或高频重试。


## v0.3.2 Klei 网页稳定性与 Chrome 浏览器补领

- Android WebView 本身使用 Chromium 渲染，不需要额外安装/打包一套 Chrome 内核。
- 科雷可见登录/领取页面增加「使用 Chrome 打开科雷页面（人工补领）」按钮，优先使用已安装的 Chrome Custom Tab，并在不可用时使用默认浏览器。
- **浏览器登录与 App WebView Cookie 不共享**。如果希望继续在后台尝试自动领取，仍需要在 App 内 WebView 登录一次科雷；仅通过 Chrome 登录并不能让隐藏 WebView 自动登录。
- 后台自动领取复用 WebView 实例，减少频繁创建销毁；对页面导航网络错误 / HTTP 5xx 在未点击领取按钮前最多重试 **1 次**，保留失败原因供查看。
- 一旦自动操作点击领取按钮，**不会自动重试网页提交或再次点击领取按钮**，避免重复操作；结果不能验证时提示人工核查。
- Klei HTTP 403/429 不重试，不以频繁刷新方式试图绕过服务器限制。
- Chrome Custom Tabs 是人工补领回退途径，不能用于锁屏后台 JavaScript 自动点击；Klei 自动领奖仍为实验性功能。


## v0.4.0 · Klei App 内领取稳定性

- **所有 Klei 登录、领取、补领都在 App 内 WebView 完成**；不使用 Chrome Custom Tabs，也不需要每次切换到外部浏览器。
- 使用 Android WebView 共享的 Cookie 持久化存储，并在完成导航与离开网页登录页时调用 CookieManager.flush()；正常版本覆盖升级不会主动清理登录 Cookie。但科雷或游戏平台让登录过期、要求双重验证时无法阻止重新登录。
- 自动领取使用同一个 WebView 实例，并允许 **未点击任何领取按钮前** 最多两次有界导航重试（短暂网络失败或 HTTP 5xx），对 HTTP 403/429 不频繁重试。
- 领取链接与执行状态保存在本机；前台服务恢复时只恢复尚未执行领取点击的任务，不重放可能已提交的领取请求。
- 发现新礼物时短暂保持 CPU 活跃，以提高屏幕熄灭期间进行网页加载的机会；即使没有启用全时高耗电模式，也可为领奖短暂获取定时唤醒锁。
- 自动领取的成功/失败/需重新登录/未知状态均发系统通知，保留 App 内查看入口与历史。
- **已点击领取并不代表领取成功**；如果确认不了结果，标记为“未知/待核实”，不重复提交一次性领取操作。
- Android 后台 WebView 渲染、网络、科雷的登陆/令牌时效和风控仍不能完全控制；该版本优先减少失败和保存恢复信息，不承诺100%抢到限量礼物。


## v0.4.1 · 同一动态多 Klei 链接与未点击重试

- 一条 UP 主动态中的**所有不同的有效 Klei creatorlink/link URL**都会分别写入本地领取记录、发送发现通知，并作为**独立领取任务**批量进入队列；同一 URL 重复出现会去重。
- API 通道在最近两条图文动态中合并完整 Opus 内容的所有链接，详情响应缓存 120 秒降低访问次数；WebView 通道加大动态内链接扫描上限。
- **未执行领取点击**时，不会因为单次网页加载超过 35 秒或页面脚本迟迟不出现就放弃：任务保持 pending；在 4、8、15、30、60 秒（最高 60 秒）的每链接退避后继续进入页面。
- 某个链接正在等待重试时，其他链接可以先使用 WebView 尝试领取；多个礼物不会永久被前一个卡住的页面堵住。
- 点击领取之前，网页证实登录失效、礼物已领完/失效、HTTP 403/429 时停止该 URL 自动重试，以避免盲目请求；用户可在 App 内检查。
- **一旦领取点击可能已经提交**，禁止自动重放领取操作。点击后的页面未能明确证明成功会记为 uncertain 并通知用户手动核实。
- 未点击领取且挂起的任务会持久保存，服务重启后可恢复；正常 App 内 Cookie 保留且不依赖 Chrome 浏览器。
- 单次加载失败时重试是有退避的网络访问，不会绕开 Klei 或 B站风控。后台 WebView 的 Android 生命周期限制仍然存在，实际领取结果须在设备上验证。


## v0.4.2 · 登录误判修复与本机领取诊断

- 普通账户路径、跨域跳转和排队/验证页面不再直接判为登录失效。只有连续至少 3 次、持续至少 3.5 秒观察到登录表单或明确登录入口与提示，才暂停为需要登录。
- 普通页脚登录文案不会拦截有效领取按钮；无法明确识别的页面保持等待并按原有退避重试，不声称登录失效。
- 区分“明确被其他人领取”“本账号领取成功文案”和“已领取但归属不明”。归属不明不会记成本账号领取成功。
- 修复记录中的“重试未提交领取”被旧状态拦住的问题。重新登录后可对未提交记录手动重试；可能已提交的请求仍不自动重放。
- 首页新增“查看 / 导出领取日志和截图”：记录发现链接、加载次数、页面路径（删除 query/fragment）、HTTP 错误、识别状态、点击派发、脚本返回与最终结果及时间。不会保存 Cookie、密码、表单输入或整页 HTML。
- 结束或首次/每五次重试时尝试绘制 WebView 截图；仅在 Klei 礼物路径且未包含密码/验证码输入框时截图，其他登录提供商不截图。截图是尽力而为，离屏渲染/页面跳转时可能空白或无法获得，不能单独作为领取成功证据。
- 截图可能包含账号名与礼物地址，仅保存在应用私有存储；最多 20 张且合计约 10 MB。日志单文件约 512 KB，保留一份轮转备份。可清空，也可通过系统文件选择器导出 ZIP，分享前请检查。
- 识别回归测试：`node --test KleiGiftWatcher/tests/claim-page.test.cjs`（仓库根目录）。测试模拟 DOM 状态，不代表实测科雷账号领取成功。
- 构建：Java 17+、Gradle 8.9、Android SDK 35/build-tools 35.0.0；仓库根目录执行 `gradle --no-daemon -p KleiGiftWatcher :app:assembleDebug :app:lintDebug`。
- GitHub 工作流在 `klei-gift-watcher-diagnostics-v0.4.2` 分支推送时构建，沿用四个 `KLEI_*` Actions Secrets。覆盖旧版本请选择 `KleiGiftWatcher-fixedsigned-apk`；普通 debug APK 的签名可能与旧安装不同，不要为安装它先卸载旧版，以免丢失登录与记录。


## v0.4.3 · 一秒网页检测

- 按要求把动态网页检测默认值和可设置下限改为 1 秒，界面与输入校验同步允许 1～3600 秒。
- 覆盖安装后首次读取设置时将旧的检测间隔迁移为 1 秒，仅执行一次；之后手动保存的间隔会保留。
- 一秒是网页检测调度间隔；已有导航未结束时不会启动重叠加载或中断当前页面，实际检测速度仍受网络和页面渲染影响。
- 备用 API 仍为 30～90 秒，HTTP 412/429 等既有访问限制与冷却处理保留。此设置不保证抢到礼物，可能增加耗电与限流概率。
